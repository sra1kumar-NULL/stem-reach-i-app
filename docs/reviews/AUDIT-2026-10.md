## 1. Blockers

### B1 — Anyone can self-register as a **teacher** (privilege escalation; minors' data exposed)
- `core/src/contracts.ts:214` — `SignupRequest.role: ROLE` accepts `"teacher"`.
- `api/src/routes/auth.ts:18,35` — the role is taken from the unauthenticated request body and written to `profiles.role`.
- `mobile/src/app/signup.tsx:21,87-90` — UI offers a Student/Teacher toggle.
- Verified: `SignupRequest.safeParse({…, role:"teacher"}).success === true`.
- Impact: a public, unauthenticated caller gets a teacher token and can then read **every student's name and performance** (`/api/reports/*` have no org/class scoping), overwrite today's activation for the whole school (`POST /api/activations`), and author questions. Violates AGENTS #5 ("never accept … owner field from the client" — role is the strongest such field) and the HLD §7 decision "teacher-created accounts".
- Fix: drop `role` from `SignupRequest` (force `student`), or gate teacher creation behind an invite code / admin-only CLI (`scripts/src/create-users.ts`). Remove the toggle in `signup.tsx`. Add rate limiting (see B4).

### B2 — `DELETE /api/questions/:id` always returns 400
- `api/src/routes/questions.ts:125` — `DeleteQuestionParams.parse(c.req.param("id"))` parses a **string** against `z.object({ id })`.
- Verified: `DeleteQuestionParams.safeParse("<uuid>")` → `false, "Expected object, received string"`.
- Fix: `DeleteQuestionParams.parse({ id: c.req.param("id") })` (or `c.req.param()`). Add an integration test — this would have been caught by any single request.

### B3 — EAS (preview/production) APKs point at `http://localhost:3000`
- `mobile/eas.json:14-17,25-28` sets only `EXPO_PUBLIC_SUPABASE_URL/ANON_KEY`; no `EXPO_PUBLIC_API_URL`.
- `mobile/.env` (has `EXPO_PUBLIC_API_URL=https://…`) is gitignored (`mobile/.gitignore:7`) and there is no `.easignore`, so EAS cloud builds don't receive it.
- `mobile/src/api/client.ts:15-23` then falls back to `Constants.expoConfig.hostUri` (absent in a release build) → `http://localhost:3000`. Every API call from an installed APK fails (Android also blocks cleartext HTTP by default).
- Fix: add `EXPO_PUBLIC_API_URL` (https) to each EAS profile (or EAS env vars); make `getApiBaseUrl()` throw a visible config error in release builds instead of silently using localhost.

### B4 — Public Supabase anon key + unknown RLS on older tables + public demo teacher password
- `mobile/eas.json:16,27` embeds the Supabase URL and **anon** JWT for project `cihobqescuhuxtiogivb` — the same project as `api/.env` and `dummy-creds.json`.
- The anon key is public by design (it ships in every APK), so it is **not** a secret leak by itself. Safety depends entirely on RLS being enabled on **every** table. The repo cannot prove that: there are no migrations in the repo; `docs/DEPLOY.md:96-107` shows RLS only for `review_states` and `questions` and explicitly says "older tables were created by hand — audit every existing table for RLS". If `profiles`, `submissions`, `streaks`, `daily_sets`, `daily_set_sections`, `chapters`, `sections` lack RLS, anyone can read/write them through PostgREST with the anon key, bypassing the API (AGENTS #1). `submissions`/`streaks` writes would let a student forge scores.
- `dummy-creds.json` + `scripts/src/create-users.ts:8,16` publish `teacher@stemri.local / Stemri@2026` for that same project. If those accounts exist on the project the APK talks to, anyone reading the repo is a teacher.
- No rate limiting anywhere (`api/src/app.ts` has none): `/api/auth/signup` can mass-create pre-confirmed users (`email_confirm: true`, `auth.ts:23`); `/api/submissions` is unthrottled.
- Fix: (1) run the RLS audit and commit the result as SQL in `docs/DEPLOY.md` (and ideally a `drizzle-kit` migration folder); (2) separate demo project from pilot project, or delete/rotate demo teacher password on the pilot project; (3) add per-IP rate limiting to `/api/auth/*` and per-user limiting to writes; (4) restrict CORS (`app.ts:19` is `origin: "*"`).

### B5 — Mobile typecheck and lint gates are red on a clean checkout
- See §0. Every PR gate listed in `docs/06-FEATURE-PLAN.md` §0 ("`npm run typecheck` … `npm --prefix mobile run lint` must show green") currently fails. Fix the install + typed-routes generation before landing anything else, otherwise later regressions are invisible.

## 2. Major — correctness / logic

### M1 — "Today" is the **UTC** date everywhere; the pilot runs in IST (+05:30)
- Server: `api/src/routes/feed.ts:17`, `submissions.ts:82-83,122`, `me.ts:13-14`, `activations.ts:10-12`, `reports.ts:17,144,153`.
- Client: `mobile/src/app/(teacher)/participation.tsx:36`, `(teacher)/reports.tsx:26-34` (mixes local `setDate` with UTC `toISOString` — off-by-one window), `(self-study)/index.tsx:63,96`, `mobile/src/lib/sm2.ts:29-36`.
- Between 00:00 and 05:30 IST the server's "today" is yesterday: a student revising after midnight sees yesterday's set and gets the streak credited to yesterday; a teacher activating before 05:30 activates yesterday's date; performance "Today" queries a UTC window (`reports.ts:92-93` compares `timestamptz` to `::date`, i.e. DB session TZ).
- Verified for `sm2.ts`: with `TZ=Asia/Kolkata` at 02:00 local, interval 1 → `due_date = 2026-10-03` (same day) — the card is due again immediately.
- Fix: one `core` helper `schoolDate(now, tz = "Asia/Kolkata")` (Intl.DateTimeFormat with `timeZone`), used by every route; app-local date helper for self-study (`toLocaleDateString('en-CA')`-style, not `toISOString`). Longer term `orgs.timezone` (feature plan PR-01).

### M2 — SRS reviews only appear if the teacher re-activates the **same** section today
- `api/src/routes/feed.ts:28,35` returns `empty` when no set exists for today, and `feed.ts:75` filters due reviews with `inArray(questions.sectionId, sectionIds)` (today's sections only). `me.ts:25-51` mirrors this.
- Consequence: a card due in 3 days is never shown unless that exact section is activated that day; spaced repetition silently degrades into "random revisit". Due cards accumulate invisibly (`me.srs.due_today` stays 0 on non-activated days).
- Fix (product decision needed): serve due reviews from any section the student has history in, independent of today's activation — requires submissions to accept a review without a `daily_set_id` or with a synthetic "review" set. Document the decision in an ADR.

### M3 — Displayed streak is never decayed
- `api/src/routes/me.ts:69-73` returns `streaks.current` as stored. The value only changes on the next submission (`submissions.ts:88-92`). A student who last practised a week ago still sees "🔥 12".
- Fix: in `/me` compute `current = lastActiveDate >= yesterday(schoolDate) ? current : 0` (pure function in `core`, unit-tested).

### M4 — Concurrent duplicate submission → 500 instead of idempotent replay
- `api/src/routes/submissions.ts:177-183` reads, then `204-207` / `225-229` plain `insert(submissions)`. Two in-flight requests (double tap, retry after timeout — `apiFetch` has no timeout) both see no row; the second hits `submissions_student_question_set_unique` → unhandled `23505` → `errorHandler` 500. The `touchStreak`/`touchReviewState` comments claim race-safety, but the submission insert itself is not.
- Fix: `insert … onConflictDoNothing().returning()`; if nothing returned, re-read the existing row and return it (and skip streak/SRS writes). Integration test with `Promise.all` of two identical POSTs.

### M5 — Submissions accepted for any daily set, past or future
- `submissions.ts:159-174` only checks the set exists and the question belongs to it. A student can answer yesterday's (or a pre-activated future) set; each new submission calls `touchStreak` for *today*, and inflates past participation reports. Also no `question.enabled` check (`:168-173`).
- Fix: require `set.setDate === schoolDate()` (or an explicit grace window), reject disabled questions.

### M6 — Activation is non-atomic; duplicate/unknown section ids wipe the day
- `api/src/routes/activations.ts:73-78` deletes all `daily_set_sections` then inserts, outside a transaction. `ActivateRequest` (`core/src/contracts.ts:136-139`) does not dedupe `section_ids` and does not check they exist. Verified: `{date:"2026-02-30", section_ids:[id,id]}` passes Zod. A duplicate id → PK violation, an unknown id → FK violation → 500 **after** the delete committed → today's set has zero sections → every student's feed becomes `empty`.
- Invalid calendar dates (`2026-02-30`) pass the regex and 500 at Postgres. `GET /activations?date=` (`activations.ts:85`) is not validated at all (AGENTS #2).
- Fix: wrap in `ctx.db.transaction`, dedupe ids (`z.array(...).transform(a => [...new Set(a)])`), verify all ids exist (400 otherwise), use a real date schema (`z.string().date()` in zod ≥3.23) shared by activations and reports.

### M7 — Summary screen is wrong after reopening the app
- `mobile/src/app/(student)/index.tsx:91-104`: if the feed loads already `completed`, it navigates with `correct = stats.correct (0)` and `attempted = feed.progress.answered` → summary shows "0/5 correct · 0% 💪".
- The streak passed to summary (`index.tsx:100`) is the value loaded **before** today's answers; `summary.tsx:75` renders the param instead of `me.streak.current` it already fetches (`summary.tsx:22-24`). First session of the day shows yesterday's streak.
- Fix: when arriving completed, render a "done for today" variant without a score (or fetch today's score from the API); render `me?.streak.current ?? param`.

### M8 — `/api/me` `totals.accuracy` is a **string** (contract drift)
- `api/src/routes/me.ts:20` uses `coalesce(avg(...), 0)` → Postgres `numeric` → node-postgres returns a string (`"0.6667…"`). `MeResponse.totals.accuracy` (`contracts.ts:204`) is `z.number()`. `reports.ts:133-134` already wraps the same expression in `Number()`, confirming the pattern. Latent today (mobile doesn't render it), breaks the first consumer that does `.toFixed()`.
- Fix: `Number(totals?.accuracy ?? 0)` or `::float8` in SQL; add a response-schema assertion in integration tests (`MeResponse.parse(body)`).

### M9 — Core SM-2: repeated "hard" never grows the interval
- `core/src/srs.ts:54-59`: `intervalDays * 1.2` rounded — from 1 → 1.2 → 1, from 2 → 2.4 → 2. Verified: six consecutive `hard` grades give intervals `1,1,1,1,1,1` while ease sinks to 1.60. (Mobile UI doesn't currently offer "hard" in the feed, but `SELF_EVAL` accepts it and old/new clients may send it.)
- `clampEase(NaN)` returns `NaN` (`srs.ts:71-73`); a corrupted state produces `{ease:null, intervalDays:null}` → DB insert error. Verified.
- Fix: `Math.max(state.intervalDays + 1, Math.round(state.intervalDays * 1.2))`; guard non-finite inputs (fallback to `INITIAL_STATE`). Add property tests (see bug-hunt plan).

### M10 — Self-study review ignores due dates; "Hard" is a lapse
- `mobile/src/app/(self-study)/review.tsx:50-53` loads **all** cards of the deck (`ORDER BY due_date`), not `WHERE due_date <= today`. Grading a not-yet-due card reschedules it from today; the "come back when they are due again" copy (`:190`) is false — reopening the deck shows every card again.
- `mobile/src/lib/sm2.ts:12-24` treats grade 2 (the **Hard** button, `review.tsx:243`) as failure: repetition reset, interval 1. In both Anki and `core/srs.ts`, Hard is a pass. Two SM-2 implementations with different semantics (PR2-REVIEW m4, still open).
- Fix: filter by due date; port self-study to `core/srs.ts` (`applyGrade` + `dueDateFor` with a local-date base), deleting `mobile/src/lib/sm2.ts`.

### M11 — Self-study is half-built: decks cannot get cards
- The only `INSERT INTO local_cards` is the starter card in `mobile/src/app/(self-study)/index.tsx:101-111`. There is no add/edit/delete card UI and no delete-deck UI, despite commit `fba682d "feat: adding cards to custom decks"`. Zettel links (`components/zettel-text.tsx:18`, `review.tsx:111-130`) require internal card ids (`card-<timestamp>`) that users never see. No ADR / LLD entry covers local SQLite as a second data store.
- Fix: add card CRUD screen or hide the feature behind a flag; document in an ADR; note feature plan PR-11/PR-13 overlap.

### M12 — `hard` is graded "incorrect" in reports but "pass" in SRS
- `core/src/contracts.ts:61-63` `selfEvalIsCorrect('hard') === false` and `submissions.ts:213-214` stores it as `need_practice`, while `submissions.ts:32-37` schedules it as a pass. Teacher accuracy and student SRS disagree for the same answer.
- Fix: decide once (likely `hard` = correct) and encode it in one `core` function used by both.

### M13 — Summary "N cards still waiting today" when the feed has nothing left
- `me.ts:36-51` counts `review_states.due_date <= today`, which includes cards graded "again" today (`intervalDays 0` → due today). The feed skips them because they were already answered in this set (`feed.ts:79`). `summary.tsx:77-82` then tells the student cards are waiting, but reloading the feed returns `completed`.
- Fix: exclude questions already submitted in today's set from `due_today`, or make "again" due tomorrow (`max(1, …)`) — pick one and test both endpoints together.

## 8. What was verified vs not

**Verified by execution:** the four gate commands in §0; `DeleteQuestionParams` string-parse failure; `SignupRequest` accepting `teacher`; `ActivateRequest` accepting `2026-02-30` and duplicate ids; SM-2 `hard` stall and `NaN` propagation; `sm2.ts` IST off-by-one (`TZ=Asia/Kolkata`); `expo-sqlite` absent from `mobile/node_modules`; `mobile/.env` and `api/.env` point at the same Supabase project; `EXPO_PUBLIC_API_URL` present only in gitignored `mobile/.env`.

**Not verified (needs a live DB / device):** actual RLS state of production tables; whether demo accounts exist on project `cihobqescuhuxtiogivb`; node-postgres returning `numeric` as string for `/api/me` (standard pg behaviour, and the `Number()` wrapping in `reports.ts` corroborates it); concurrent-submission 500 (reasoned from code, not reproduced); EAS build output; on-device behaviour.
